# 数据结构与 DataLoader 设计

核查日期：2026-09-16。依据四张 CSV、`样板/info.json`、完整样板 TXT，以及提供的平台字段说明截图。统计包含测试记录；原始文件未修改。本文保留设计依据，已实现的通用 NumPy DataLoader 位于 `sensor_loader/`，实际接口、默认值和边界以 `sensor_loader/README.md` 为准。

实现采用单进程、按文件流式解压到有界临时数组，再输出三路独立时间轴的 NumPy 批次。按用户最新要求不依赖、不安装 PyTorch，不在本机训练。下文涉及 PyTorch、多 worker 共享预算和精确时间恢复的内容属于后续训练端设计，不能视为当前已经实现的功能。

## 1. 数据集概况

| 文件               | 数据行数 | 不同 healthid 数 | 实测编码                     | 一行的含义                                            |
| ------------------ | -------: | ---------------: | ---------------------------- | ----------------------------------------------------- |
| 传感器原始数据.csv |     1165 |               40 | UTF-8（按 utf-8-sig 可读取） | 一条传感器附件记录，包含用户、时间范围和 ZIP 对象路径 |
| 用餐信息1.csv      |      288 |               41 | GB18030 可正确解码           | 一次用餐记录及问卷、图片附件索引                      |
| 用餐信息2.csv      |      169 |               31 | GB18030 可正确解码           | 同一类用餐记录的部分导出                              |
| 用户信息.csv       |       60 |               43 | GB18030 可正确解码           | 一条用户资料记录；同一用户可能有多条                  |

以上 healthid 数是平台用户标识数量，不能未经身份核对直接等同于独立受试者人数。

1165 条传感器记录的 uniqueid 和附件路径均唯一。它们是文件索引，不是 1165 个训练样本，也不代表 1165 顿饭。一个 ZIP 可以跨较长时间、有多段有效采样，并对应零次或多次用餐；一顿饭也可能跨 ZIP。

用餐表 2 的 169 个 uniqueid 全部包含于用餐表 1。除最后一条截断记录外，重叠记录在将时间统一到秒后内容一致。最后一条的 foodName 在换行处截断，后续四个字段缺失；表 1 中该记录完整。建议当前直接以用餐表 1 为用餐数据源，表 2 仅用于核对，不拼接出 457 条用餐。

## 2. 公共字段

| 字段       | 平台定义              | 训练数据处理                                                                                      |
| ---------- | --------------------- | ------------------------------------------------------------------------------------------------- |
| uniqueid   | 数据唯一 ID           | 在各自表内标识记录。传感器记录 ID、用餐记录 ID、资料记录 ID 含义不同，不能直接跨表等值连接        |
| healthid   | 用户 ID、用户唯一标识 | 跨表关联的主要平台键。另建经核对的 subject_id 表示真实受试者                                      |
| externalid | 用户自定义的外部 ID   | 通常形如 HNU21017，用于受试者映射和人工核查；实际存在拼写、大小写、空值与复用，不能直接当可靠主键 |
| uploadtime | 上传时间              | 数据上传/入库信息，用于溯源与版本核查，不作为信号时间或用餐标签时间                               |
| recordtime | 数据产生时间          | 该条记录的时间；不能代替其内部采样范围或用餐范围                                                  |

截图中 uploadtime/recordtime 定义为 Integer，但 CSV 导出已部分转换成日期文本。要兼容毫秒整数与 `YYYY-MM-DD HH:MM:SS` 两种表现形式。日期文本按本项目北京时间 UTC+8 解释，内部统一成 int64 Unix 毫秒；已有毫秒整数不要再次加 8 小时。日期文本已丢失的毫秒精度无法恢复。

## 3. 传感器原始数据表

除公共字段外：

| 字段         | 平台定义                      | 用法与限制                                                                                                    |
| ------------ | ----------------------------- | ------------------------------------------------------------------------------------------------------------- |
| groupid      | 记录分组 ID                   | 保留来源分组信息，不擅自解释成一次用餐、连续采样会话或用户 ID                                                 |
| timeStamp    | 采集数据起止时间戳，TimeFrame | 内含 startTime/endTime，当前数值为毫秒。用于文件范围初筛；真正可用区间须检查 TXT 内各模态时间戳               |
| deviceType   | 设备类型                      | 1164 条为 HUAWEI WATCH JNA，1 条空。用于设备域分析与质量检查                                                  |
| sensorData   | 传感器原始文件，Attachment    | `kitattachments/.../sensorData-....zip` 是服务器对象路径。下载后映射至本地 ZIP；模型输入来自 ZIP 内的采样值 |
| sensorType   | 传感器原始数据类型，Array     | 全部记录为`["acc","ppg"]`，但样板还包含 GYRO 字段，应结合真实文件检查可用模态                               |
| recordschema | 元数据版本                    | 当前全为 1。保留在缓存配置和解析版本检查中                                                                    |

timeStamp 是 Python 字典风格文本，如 `{'startTime': ..., 'endTime': ...}`，使用受控 JSON/Python literal 解析，不能简单按逗号拆分，也不能使用 eval。

传感器表范围为北京时间 2026-07-09 18:53:12 至 2026-08-02 19:47:51。文件声明时长中位数 4421 秒，最短 205 秒，最长 945805 秒（约 10.95 天）。最长记录属于 HNU21004，应复核其真实采样范围。

同一 healthid 下有 61 条记录与此前某条记录的声明时间范围重叠。逐条相加约 3317.27 小时，按用户合并时间区间约 3258.19 小时。这两个数都不是有效信号时长，不能直接用于训练规模或佩戴时长结论。

除公共字段外，两张表具有相同业务字段：

| -------------- | -------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| dietaryType    | 饮食类型             | 早餐、午餐、晚餐、上午/下午/晚上加餐。是用餐事件属性；并非逐口动作标签                                                                |

| satiety        | 饱腹情况             | 刚刚好、有点撑、没吃饱。可作单独的事件级预测目标，不作为进食识别的默认输入                                                            |

| tablewareType  | 餐具类型             | 筷子、刀叉、勺子、手、无需餐具。适合按餐具分层评估或多任务标注                                                                        |
| dietaryHand    | 饮食惯用手           | 左手/右手。用餐动作和手表所在手是否一致会影响信号                                                                                     |
| wearHand       | 设备佩带手           | 本次用餐填写的左手佩戴/右手佩戴，属于事件级上下文                                                                                     |
| diningPictures | 用餐图片，Attachment | 图片 ZIP 对象路径。当前传感器样板不是该图片附件的样板，内部图片格式和前后餐对应规则尚未核查                                           |

表 1 中：晚餐 129、午餐 117、早餐 27、晚上加餐 10、下午加餐 4、上午加餐 1。用餐时长中位数 928 秒（15 分 28 秒）；6 条小于 60 秒，最短 2.16 秒。它们可能是误操作、时间填报问题或特殊记录，应保留质量标记，不能未经检查全部当作可靠短餐。

标签粒度只到“某段时间在用餐”。这些记录不能直接提供每次抬手、每一口、咀嚼或吞咽动作的真值。

60 行对应 43 个 healthid，其中 11 个 healthid 有多条资料。按 healthid 分组，身高、体重、年龄、佩戴手分别有 5、7、3、2 个分组出现不同值。不要把用户表直接 merge 进每条采样，造成行数成倍增加。

先核对受试者映射，再选择与采集时间匹配的资料版本，记录匹配方式。需要严格模拟当时可用信息时，采用采集时间之前最近的资料；没有历史记录则标缺失，不静默使用未来资料。资料中的佩戴手和用餐填写的佩戴手冲突时，分别保留并标记来源。

## 6. ZIP 结构

```text
sensorData-....zip
├── info.json
└── collect_data0_1784621258_1784634352.txt
```

info.json 包含 files 文件清单、filename、contentype、metadataname、metadataversion、timestamp，以及 projectcode、uploadid。样板的 metadataname 为 SensorOriginalData、版本 1。其 timestamp 为 2026-07-21 20:15:00.912+08:00，是文件元信息时间，不能替代采样时间；采样本身最晚在 19:45 左右结束。

通过文件名时间范围和 uploadid，可对应传感器表中 HNU21017 的记录：

- uniqueid：`F0:FA:C7:49:6A:8B_1784621258_1`
- ZIP：`sensorData-1784636100913-0febac83964a4034bb6774a4c433c97a.zip`
- CSV 声明范围：2026-07-21 16:07:38 至 19:45:52。

TXT 使用制表符分隔，包含 499221 行数据、53 列，无空单元格，本样板全部为整数：

| 字段                     | 数量 | 含义                                                          |
| ------------------------ | ---: | ------------------------------------------------------------- |
| ACC_TIME                 |    1 | 加速度数据对应的时间戳                                        |
| PPG_TIME                 |    1 | PPG 数据对应的时间戳                                          |
| GYRO_TIME                |    1 | 陀螺仪数据对应的时间戳                                        |
| ACC_X / ACC_Y / ACC_Z    |    3 | 三轴加速度原始值                                              |
| GYRO_X / GYRO_Y / GYRO_Z |    3 | 三轴角速度原始值                                              |
| PPG1–PPG44              |   44 | 导出的 PPG 字段，具体光源/探测器/辅助通道映射尚需设备协议确认 |

ACC 和 GYRO 合起来可作为六轴 IMU 输入。坐标轴物理方向、量程、缩放系数、PPG 各字段的物理语义没有出现在这些文件中，不应自行转换成 m/s²、rad/s 或指定某列是绿光/红外。

### 有效数据、重复时间戳和中断

| 模态 | 时间戳 > 0 的行数 | 时间戳为 0 的行数 | 同时间戳批次的常见样本数 | 相邻批次的常见时间差 |
| ---- | ----------------: | ----------------: | -----------------------: | -------------------: |
| ACC  |            463159 |             36062 |                       10 |                94 ms |
| GYRO |            462790 |             36431 |                       10 |                94 ms |
| PPG  |            108225 |            390996 |                       15 |               602 ms |

本样板中，某模态时间戳为 0 时，对应的全部信号字段也为 0。这表明这些行没有该模态有效样本。应按模态单独过滤并保留缺失信息，不能将它们作为真实零信号参与标准化。

重复时间戳下的信号值会变化，应保留全部样本及其批内顺序，不能按 timestamp 去重。相同文本行也不能被默认解释为三个模态严格同步，尤其在启动和缺失阶段。

按稳定批次的“批内样本数 / 批次时间差”估计，ACC/GYRO 约 106 Hz，PPG 约 25 Hz。这是文件观测估计，不是已经确认的设备标称采样率。需要确认批次时间戳表示首样本、末样本还是回调时刻，才能恢复逐样本时间。不能直接按 100 Hz 和 25 Hz 从文件起点连续编号。

PPG1–20 在本样板中有非零值，PPG21–44 全部为 0。仅能得出该样板的结论。全量扫描并确认协议前，不应永久删除后 24 个字段。

ACC 实际首尾为 16:07:32.256 至 19:45:51.836，跨度 13099.58 秒；以相邻批次间隔 > 1 秒作此次诊断的分段阈值，得到 9 段，段内首尾跨度合计约 4348.65 秒（72.48 分钟）。最大片段间隔约 92.66 分钟。这是用于揭示中断的近似统计，未补偿批内时间，不是精确佩戴时长。1 秒是诊断阈值，正式分段阈值应按模态批次周期配置。

对应的晚餐区间为 18:35:57 至 19:03:50。虽然完全落在 CSV 声明的文件范围内，样板中 18:37 至 18:39 附近仍存在采样缺口。因此“附件时间范围覆盖用餐”不等于“信号完整覆盖用餐”。

## 7. 三类数据怎样关联

训练数据以传感器数据为主表（按用户确认的规则）。只从可用的传感器记录及其有效采样段生成训练窗口，用户资料和用餐记录作为附加信息，不单独生成训练样本。

- 用户资料：只关联传感器主表中存在的 healthid，并按资料版本规则选择记录；没有对应传感器数据的资料直接忽略，不进入训练索引。
- 用餐信息：按相同 healthid 和时间区间交叠关联。没有对应传感器数据的用餐直接忽略；只有部分交叠时，仅对实际有信号的部分生成标签。CSV 声明范围用于初筛，最终以附件内有效采样区间为准。
- 传感器记录：不因没有用餐交叠而删除，保留为窗口候选；无用餐标注的窗口按标签可信度规则处理，不自动视为非用餐。缺少资料时保留缺失标记，不通过内连接丢弃信号。
- “忽略”仅指不参与训练索引和标签构建，不删除或修改原始 CSV。辅助表的孤立记录不阻塞 DataLoader 构建，也不需要先补齐这些记录。

```text
传感器 CSV ── uniqueid + sensorData ── 本地 ZIP / 原始信号
     │                                     │
     │ healthid + 真实时间区间               │ 各模态有效区间
     ▼                                     ▼
用餐表 1 ───── timeFrame ─────────────── 带标签的信号窗口
     │                                     ▲
     └── healthid + 经核对的 subject_id ─────┤
                                           │
用户资料 ── 受试者映射 + 资料时间版本 ────────┘
```

40 个传感器 healthid 在用餐表和用户表中都能找到；用餐表有 1 个 healthid 没有传感器记录。只按 healthid 和 CSV 声明范围计算，288 顿饭中 269 顿完全覆盖、5 顿部分覆盖、14 顿没有覆盖。这里还没有用全部 ZIP 的有效采样区间复核。

身份字段存在需先核对的情况：跨四张表有 13 个 healthid 对应多个 externalid；HNU21007、HNU21040 各自对应两个 healthid。也有 HNU21028/HNU21029、HNU21018/HNU21043 这样不能仅按拼写差异解释的组合。应区分输入错误、账户变更和账户复用。

建立显式 `subject_mapping`，保存 healthid、externalid_raw、subject_id、适用时间范围、核对状态。大小写和首尾空格可规范化，但不要自动把不同编号合并为同一受试者。

训练/验证/测试必须按核对后的 subject_id 分组。在映射尚未核对时，可暂时将共享 healthid 或相同有效外部编号的关联记录放入同一防泄漏组，或隔离身份不明记录。不要随机按 ZIP 或滑动窗口划分；同一个人的相邻窗口不能落入不同集合。防泄漏分组不等于确认这些记录属于同一个人。
